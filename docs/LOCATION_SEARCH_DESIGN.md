# 通用地点查询与覆盖边界

用户要求：不能按“这次缺什么就补一个专用工具”修补；应让地点查询适用于新的公司、品牌、楼宇和别名。此原则已写入项目 `AGENTS.md`。

## 已实现

Agent 使用同一个 `resolve_place` 接口，根据查询结果选择名称／别名、地址或数据来源。没有 TikTok 地址表，也没有针对某家公司增加工具。

- `source=map` 查询实际 Pelias 地图地址库。保留严格地点匹配，避免把“Singapore office”返回的其他办公室当成目标公司。
- `source=registry` 查询 GLEIF 的真实新加坡法人记录，取其总部／登记地址，再通过地图服务定位。它是数据来源适配器，不是办公室知识表。公司关联和地图坐标分别保留来源证据。
- 查询为空后把结果反馈给 Agent，允许换查询或来源，而不是自动结束并要求用户重填已给出的目的地。
- 用户只是在重试失败查询时，新查询不会被上次保存的搜索词覆盖。已经确认某个地图候选时，仍复用原查询和来源来核对地点身份。
- 公司来源的地址一律要求确认，显示地址来源链接，并注明总部／登记地址不一定是用户的实际办公地点，地图仅定位楼宇／街道，未核实楼层及入口。
- 泛指沿途店铺仍走自动 POI 搜索和候选比较，不转为公司或门店地址确认。

接口来源定义见 [GLEIF 官方 API 说明](https://www.gleif.org/en/lei-data/gleif-api/)。该来源只覆盖其法人记录，不是完整的公司办公室目录；来源没有记录时不生成地址。

## 为什么不能承诺完全识别

语义理解与实际数据覆盖是两个问题。LLM 可以改写查询和决定下一次查什么，不能补造地图未收录的办公室，也不能知道“家”“我的公司”等私人位置。同名分店、搬迁或不同办公楼也需要确认。

要显著扩大商业 POI 和自然语言查询覆盖，应选择成熟的地点搜索服务作为通用检索源，再由同一个接口返回候选。例如 [Google Places Text Search](https://developers.google.com/maps/documentation/places/web-service/text-search) 支持文本地点、地址和商业场所查询，但需要服务配置；项目尚未接入，不能把未来能力作为本次验收结果。集成时还需处理地图展示与数据保存：[Google Places 官方政策](https://developers.google.com/maps/documentation/places/web-service/policies) 对其地图展示及缓存有要求，不能直接将其结果长期存入现有记录并画在 OSM 地图上。

更完整的数据源能减少逐案修补，但任何来源都有覆盖和新鲜度限制。最终行为应是“通用检索、改写与重试、来源核验、必要时确认”，而不是“保证任何输入都能识别”。

## 通用网页检索与来源核验（2026-10-05）

新的失败记录 `20261005T105456-316dc95d` 已试过英文别名与 GLEIF，但所有来源为空，Agent 随后要求用户重填已经给出的“新加坡 OpenAI 的公司”。这说明地图和 LEI 登记覆盖不足；先前的修复没有形成完整的商业办公室检索能力。

用户选择接入通用网页检索，并在本地配置了 Tavily 凭据。`resolve_place` 仍是统一接口，现在支持 `source=web`，分两阶段：

1. 根据 Agent 选择的关键词调用 Tavily，返回有来源 URL、实际网页内容、文档 ID 和检索证据的有限文档集。未配置、限流、权限或来源读取失败保留独立错误，不能冒充“没有地点”。
2. Agent 从原文识别公司及办公楼，提供文档 ID、公司名、地点名和准确引用。后端校验引用确实存在且包含对应名称，再交给 Pelias 定位。坐标仍来自地图服务；楼内花园等附属地点在有完全同名办公楼时被过滤。所有公开来源线索需要确认实际目的地，不证明楼层、入口、当前租户或用户的办公地点。

网页内容是数据，不是指令。拟搬迁地点、活动场地、同名法人和登记地址不能被模型直接认定为办公室。不得通过模型生成引用、坐标或品牌地址表弥补缺失数据。原文引用核验失败会回到 Agent 重试。

检索记录保留逐次查询与来源的结果，避免最后一次空查询覆盖全部历史。用户已提供目的地时，未查询就要求重填会被拒绝；确实没有候选时说明已尝试的来源与配置／覆盖缺口，替代笼统的“要去哪里”。已有起终点、十分钟停留和偏好仍通过澄清延续。

Tavily 凭据只在本地 `.env` 的 `TAVILY_API_KEY` 中配置，使用后端 Authorization header，不写入工具参数、请求正文或缓存。协议依据：[Tavily Search 官方文档](https://docs.tavily.com/documentation/api-reference/endpoint/search)。

真实浏览器记录 `20261005T111016-96678fbd`：Agent 自动尝试 map、registry、web；网页引用第一次未通过核验后，自主修正为实际报道原文，生成唯一的 `OpenAI · CapitaSpring, Raffles Place, Singapore` 候选，附 [Business Times 来源](https://www.businesstimes.com.sg/property/openai-steps-singapore-footprint-talks-lease-100000-sq-ft-shaw-tower)。记录含实际 Tavily 和 Pelias 响应证据，保留 600 秒加油停留，只询问 `destination_place_id`，不再要求用户手动提供地址。没有替用户确认办公室，也未继续生成这次行程的最终路线。

同一办公地点及搬迁讨论也见 [JLL 2026-09-28 新闻稿](https://www.jll.com/en-sea/newsroom/cbd-office-tightness-drives-another-quarter-of-rental-growth-as-vacancy-hits-near-three-year-low)。这是公开线索，不是当日办公室入口核验。

该链路通用于新公司与楼宇。对于数据不公开、来源错误或搬迁未更新的地点仍有覆盖边界。网页检索 API 本次已实际验证，不代表能保证识别所有公司办公室。

## 研究、审阅与候选选择（本轮通用修复）

`resolve_place` 现在区分研究阶段和提交候选阶段。模型调用默认 `present_candidates=false`，先得到真实候选名称、类型、区域与来源，仍可自主改写别名、继续搜索或换来源。之后用同一角色曾返回的 `candidate_ids` 提交最多五个相关候选，由用户选择；可用 `reject_candidate_ids` 排除无关结果。不是每得到一批地图结果就立即结束并把附近所有设施都交给用户判断。

候选与起点／终点分别绑定，不能用另一角色、任意 POI 或生成 ID 代替。每个候选保存实际搜索来源、关键词及网页证明，确认后重放所选候选自己的查询；后续空查询不会覆盖先前有效候选的来源。公开来源证明仍需再次核验。已有未排除候选时禁止要求重填原地点；无候选且 Tavily 已配置时，在请求补充描述之前必须尝试网页来源。真正无关的候选可以排除，避免被迫选择错误地点。

起终点在提取工具的 schema 中要求明确提供（缺失时可为 null），并标明“名称不熟悉不等于未提供地点”。提取修复不能丢失已给出的地点描述。产品候选表列出实际名称、地址或区域与来源，别名／拼写／描述等匹配理由标明是 AI 的解释，最终地点仍由用户确认。

真实通用检索回归：未添加地点专用规则，Agent 将“新加坡艺术科学博物馆”匹配为 `ArtScience Museum, Bayfront Subzone, Singapore`，将“南洋理工大学”匹配为 `Nanyang Technological University, Murai, Singapore`，并各自审阅后提交一个相关候选。记录分别为 `outputs/20261005T152342-7ff8ad4c/result.json` 和 `outputs/20261005T152342-b8c34a85/result.json`。它们验证真实名称检索与候选提交流程，不代表路线或所有私人地点都可覆盖。环球影城、Hotel 1900 和 LTA 的本轮故障与完整行程回归另见 [地点提取与 LTA 展示修复](ENDPOINT_EXTRACTION_LTA_FIX.md)。

命名的业务经停也通过 `search_pois search_names` 接受同一品牌／分店的语言或拼写假设，原始 `poi_name` 不改写。OSM 的真实 `name:*`、`brand:*` 语言名称和类别参与核对，模型生成的别名不写入 `Place.names`；`Place.names` 仅保存来源名称。最终名称检查核对实际地图名称，并保留原始要求及别名解释；通用类别经停不允许被别名机制改成指定品牌，不要求用户填写具体门店地址。原始名称、查询假设和实际门店 ID 保留在搜索记录中。

最终完整回归为 300 项通过，包含中文品牌与英文地图名称的经停查询、真实多语言名称读取，以及原始二十分钟停留和其他约束不被改写。

最终网页原始描述回归：`outputs/20261005T154422-924111f6/result.json` 保留“环球影城”，经真实名称检索和 AI 相关性审阅后仅提交 `Universal Studios Singapore, Sentosa, Singapore` 候选，网页提供选择并展示来源；没有要求重写起点。
