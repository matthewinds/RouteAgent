# 用户确认的主要目标

用户于 2026-10-05 确认：RouteAgent 应是自主使用真实工具、验证结果并重新规划的出行 Agent。后续修复和扩展以以下五步为依据。

1. **理解用户出行需求。** 用户用自然语言描述行程，例如“从 A 到 B，30 分钟内到达，希望避开拥堵，并经过一家咖啡店”。Agent 提取起点、终点、时间、交通方式、必需条件和偏好。保留原意，区别硬约束和偏好。
2. **获取地图与实时信息。** Agent 根据当前需求和已有结果，自主决定调用哪些工具，而不是人工固定查询所有来源。可使用 OpenStreetMap 道路和 POI、OSRM／OSMnx 路线计算、LTA DataMall 交通与停车、Open-Meteo 天气、地址定位服务、OneMap 公交／地铁，以及其他经验证的数据源。工具可用性与接入状态如实报告。
3. **生成多条候选路线。** LLM 决定需要比较什么，例如服务估计最快、最短、避高速或经停 POI 的候选。路径计算由地图工具完成；不能让 LLM 编造路线。只有工具提供支持时，才声称取得相应类型的路线。
4. **验证并自动重新规划。** 后端检查时间限制、交通状况、指定地点或类别、累计步行距离、天气偏好等。Agent 依据具体失败原因重新查询、调整候选并再次验证，形成 Planning → Tool Use → Verification → Replanning 闭环。重规划不能删除用户的重要约束。调用与时间预算有限，未知条件保持未知。
5. **选择并解释最终路线。** 综合时间、距离、交通、POI 和用户偏好比较候选，选择最合适的已验证方案，并用自然语言说明实际依据、取舍和未核实项。不能把有限候选中的最好方案描述成全局最优，不能把未知实时条件说成保证。

## 自动经停的产品行为

“顺路经过一家面包店买面包”意味着系统自动找店，不意味着用户已有指定店铺。Agent 应搜索符合类别的真实 POI，为多个门店调用路线服务，比较绕行及偏好，并验证到达时限等要求。仅用户确实指定某个地址／分店且位置有歧义时才要求地点确认。

系统不知道“家”“公司”的位置时，需要用户提供位置；未说明购物停留时间且影响到达检查时，需要确认停留预留。确认这些个人事实之后，门店搜索和路线选择仍由 Agent 完成。

## 按需求比较组合出行

用户未明确限制交通方式时，应比较完整候选行程；Agent 的临时选择不能成为用户的整程限制。公交、地铁和步行可以组合，候车、换乘、接驳、经停停留及累计步行都必须计入。一个方式通过基础检查，仍可以探索其他方式；明确的用户交通限制和车辆可用性继续保持有效。

“最快”以满足硬约束的完整服务预计时间比较；“尽量避免淋雨”还应比较步行及候车、换乘的潜在暴露时间。不得凭交通方式名称断言全程有遮蔽。起终点直接查询失败时，Agent 可决定搜索真实交通站点，计算实际步行接驳并重新查询公共交通；不得编造站点、连接路径、班次或零时间换乘。接口覆盖缺口要区别于条件无解。

## 通用自然语言地点匹配

用户明确要求：输入新地点之后，Agent 应理解其大概指向的场所、类型和区域，自主提出名称／语言别名／拼写假设，再通过真实来源匹配候选供选择，不能每换一个地点就增加专用规则。用户原始描述始终保留；模型的理解是检索假设，不能冒充地址或坐标证据。

检索结果先由 Agent 审阅相关性，排除周边无关设施，再提出有来源的候选。已有候选不能退化成要求重填；现有地图名称未覆盖时，要利用已配置的通用网页来源继续寻找名称或地址。最终只选取真实服务返回、经必要确认的地点；仍无可靠结果时说明具体覆盖或服务缺口。
