# 用戶確認的主要目標

用戶於 2026-10-05 確認：RouteAgent 應是自主使用真實工具、驗證結果並重新規劃的出行 Agent。後續修復和擴展以以下五步為依據。

1. **理解用戶出行需求。** 用戶用自然語言描述行程，例如“從 A 到 B，30 分鐘內到達，希望避開擁堵，並經過一家咖啡店”。Agent 提取起點、終點、時間、交通方式、必需條件和偏好。保留原意，區別硬約束和偏好。
2. **獲取地圖與實時信息。** Agent 根據當前需求和已有結果，自主決定調用哪些工具，而不是人工固定查詢所有來源。可使用 OpenStreetMap 道路和 POI、OSRM／OSMnx 路線計算、LTA DataMall 交通與停車、Open-Meteo 天氣、地址定位服務、OneMap 公交／地鐵，以及其他經驗證的數據源。工具可用性與接入狀態如實報告。
3. **生成多條候選路線。** LLM 決定需要比較什麼，例如服務估計最快、最短、避高速或經停 POI 的候選。路徑計算由地圖工具完成；不能讓 LLM 編造路線。只有工具提供支持時，才聲稱取得相應類型的路線。
4. **驗證並自動重新規劃。** 後端檢查時間限制、交通狀況、指定地點或類別、累計步行距離、天氣偏好等。Agent 依據具體失敗原因重新查詢、調整候選並再次驗證，形成 Planning → Tool Use → Verification → Replanning 閉環。重規劃不能刪除用戶的重要約束。調用與時間預算有限，未知條件保持未知。
5. **選擇並解釋最終路線。** 綜合時間、距離、交通、POI 和用戶偏好比較候選，選擇最合適的已驗證方案，並用自然語言說明實際依據、取捨和未核實項。不能把有限候選中的最好方案描述成全局最優，不能把未知實時條件說成保證。

## 自動經停的產品行為

“順路經過一家麵包店買麵包”意味著系統自動找店，不意味著用戶已有指定店鋪。Agent 應搜索符合類別的真實 POI，為多個門店調用路線服務，比較繞行及偏好，並驗證到達時限等要求。僅用戶確實指定某個地址／分店且位置有歧義時才要求地點確認。

系統不知道“家”“公司”的位置時，需要用戶提供位置；未說明購物停留時間且影響到達檢查時，需要確認停留預留。確認這些個人事實之後，門店搜索和路線選擇仍由 Agent 完成。

## 按需求比較組合出行

用戶未明確限制交通方式時，應比較完整候選行程；Agent 的臨時選擇不能成為用戶的整程限制。公交、地鐵和步行可以組合，候車、換乘、接駁、經停停留及累計步行都必須計入。一個方式通過基礎檢查，仍可以探索其他方式；明確的用戶交通限制和車輛可用性繼續保持有效。

“最快”以滿足硬約束的完整服務預計時間比較；“儘量避免淋雨”還應比較步行及候車、換乘的潛在暴露時間。不得憑交通方式名稱斷言全程有遮蔽。起終點直接查詢失敗時，Agent 可決定搜索真實交通站點，計算實際步行接駁並重新查詢公共交通；不得編造站點、連接路徑、班次或零時間換乘。接口覆蓋缺口要區別於條件無解。

## 通用自然語言地點匹配

用戶明確要求：輸入新地點之後，Agent 應理解其大概指向的場所、類型和區域，自主提出名稱／語言別名／拼寫假設，再通過真實來源匹配候選供選擇，不能每換一個地點就增加專用規則。用戶原始描述始終保留；模型的理解是檢索假設，不能冒充地址或座標證據。

檢索結果先由 Agent 審閱相關性，排除周邊無關設施，再提出有來源的候選。已有候選不能退化成要求重填；現有地圖名稱未覆蓋時，要利用已配置的通用網頁來源繼續尋找名稱或地址。最終只選取真實服務返回、經必要確認的地點；仍無可靠結果時說明具體覆蓋或服務缺口。

## 完整 LTA 動態數據接入

用戶於 2026-10-05 要求擴展 LTA 接入。使用統一目錄和查詢接口覆蓋官方動態數據清單，由 Agent 按行程選擇數據，而不是每次固定查詢所有數據。公交到站、地鐵運營通告、擁擠程度、維護及道路事件應與真實站點、線路、時間和幾何核對，再決定是否重規劃。統計文件、有限分頁、遠期出發、接口權限和過期觀測不得冒充當前完整 ETA；不為未核實的換乘編造延誤分鐘數。
